# 8. 결정 이력

> 개발자: 박승우 · 일자: 2026-08-26
> **왜 이렇게 돼 있는지**를 적는다. 지금 상태는 나머지 문서에 있다.

같은 논의를 두 번 하지 않으려고 남긴다. 결정을 뒤집을 수는 있지만,
**뒤집기 전에 왜 그렇게 정했는지는 읽어야 한다.**

---

## 화면을 28개로 줄였다 — 2026-08-25

**전:** 화면 100개 이상. 대부분 껍데기이거나 한 번도 안 쓰인 것.

**왜:** 쓰지 않는 화면이 메뉴·권한·문서·시험을 전부 무겁게 했다.
「이 화면 살아 있나」를 매번 확인해야 했다.

**한 것:** 실제로 쓰는 28화면만 남기고 나머지 화면·표·SP·메뉴를 지웠다.
`tbl_screen` 103 → 28, 표 71 → 53, 양식 73 → 48.

**대가:** 나중에 그 기능이 필요하면 다시 만들어야 한다.
git 이력에는 남아 있다.

---

## 업무 SQL 을 전부 SP 에 둔다

**왜:** 화면이 늘어도 서버 코드는 「SP 를 부르고 결과를 담아 넘기는」 모양이 안 바뀐다.
SQL 이 자바와 XML 에 흩어지면 같은 조건이 여러 곳에 복제된다.

**규칙:** 매퍼 XML 에 직접 `SELECT` 를 적지 않는다.

**실제로 어겼을 때:** 삭제차단 SQL 이 매퍼 5곳에 복제돼 있었다.
상태 코드가 하나 늘면 여섯 곳을 고쳐야 했다 — 2026-08-26 에 공용 SP 로 내렸다.

---

## SP 를 `CREATE OR REPLACE` 로 쓴다 — 2026-08-26

**왜:** `CREATE PROCEDURE` 로 쓰면 두 번째 적용부터 실패한다.
`apply-all.sh` 는 「몇 번을 돌려도 결과가 같다」고 주장하는데 실제로는 아니었다.
운영에서 SP 하나 고치려면 손으로 DROP 해야 했다(E2E-002).

---

## 양식코드를 SP 안에 나열하지 않는다 — 2026-08-26

**왜:** 정규식 화이트리스트(`^hwp_sys_0(0[1-9]|1[0-9]|2[0-7])$`)가 SP 두 곳에 있었다.
`hwp_sys_028` 부터는 등록해도 목록에 안 떴다 — **열한 종이 조용히 숨어 있었다.**

**대신:** `tbl_template.doc_kind` 처럼 값으로 판단한다.

---

## 검토(REVIEW) 단계를 기본으로 끈다

**왜:** 상태를 4단계로 짧게 간다 — 작성대기 → 승인요청 → 승인(+반려).
검토를 켜 두면 전송한 문서가 검토 단계에서 멈춘 채 승인으로 못 넘어간다.

**남긴 이유:** 결재선 구조(`tbl_approval_line_step`)에는 3단계가 다 있고
`use_yn = 'N'` 으로 꺼 둔다. 필요한 업체는 켤 수 있다.

---

## 목록 배지를 3단계로 보여 준다

DB 상태는 `WRK`·`REQ`·`REV`·`APV`·`RJT` 다섯인데 화면 배지는 셋이다.

| 배지 | DB 상태 | 왜 |
|---|---|---|
| 전송대기 | `WRK` · `RJT` | 반려도 작성자가 다시 고칠 수 있는 상태다 |
| 전송 | `REQ` · `REV` | 결재 진행 중 |
| 결재완료 | `APV` | 끝 |

사용자에게 다섯 가지 상태를 외우게 하지 않는다.

---

## 공통코드 `main_cd`·`sub_cd` 를 UPPER_SNAKE 로 — 2026-08-25

**왜:** 표기가 섞여 있어 콤보가 비는 일이 잦았다.

**핵심:** `sub_cd` 는 **업무 표에 저장되는 값과 같은 표기**다.
`tbl_schedule_rule.nonwork_rule = 'KEEP'` 이면 `sub_cd` 도 `KEEP` 이다.
코드만 바꾸고 데이터를 안 바꾸면 라벨이 안 붙는다 — 항상 같이 옮긴다.

**대가:** 저장된 데이터까지 마이그레이션해야 했다(`04_migrate_code_upper.sql`).

---

## 신규 업체를 0000 복제로 연다 — 2026-08-26

**전:** 신규 업체 개설 경로가 아예 없었다. 메뉴·권한·부서·관리자가
0000 전용 덤프에만 있어 다른 회사는 로그인해도 빈 화면이었다.

**왜 복제인가:** 메뉴 43줄·화면권한 84줄을 `06_company_seed.sql` 에 손으로 적으면
화면이 하나 늘 때마다 두 곳을 고쳐야 한다. 0000 을 원본으로 삼으면
`02_seed.sql` 한 곳만 정본이 된다.

**안 주는 것:** `usr`(그 업체가 직접 만든 양식)은 복제하지 않는다. 남의 것이다.

---

## DB 를 배포 파이프라인에 넣지 않는다

**왜:** 스키마 변경은 되돌리기 어렵고, 배포와 같은 트랜잭션으로 묶을 수 없다.
실패하면 반쪽 상태가 남는다.

**대신:** 배포 담당이 `bash db_sasshaccp/apply-all.sh` 를 따로 돌린다.
6본 모두 재실행 안전하게 만들어 두었다.

---

## E2E 가 DB 를 직접 읽는다 — 2026-08-25

**왜:** 화면이 「저장했습니다」를 띄우고 서버가 실패를 삼킨 사고가 있었다.
결재 전 경로가 500 인데 스모크·단위 테스트가 전부 통과했다(E2E-001).

**대가:** 로컬 도구(`tools/`, git 미포함)가 필요하고 CI 에서는 그 시험이 skip 된다.
**빈 값을 돌려 조용히 통과시키지 않는다** — skip 이 낫다.

---

## 감사자료 내보내기 API 를 화면 없이 남긴다

`/api/v1/docs/audit-export/**` 는 화면이 없고 프론트도 안 부른다.
규제·감사 대비로 경로를 유지하며 `@Deprecated` 로 표시만 한다.
`tbl_audit_log`(감사로그 화면)와 **다른 기능**이라 혼동해서 지우면 안 된다.

## 문서를 25본에서 8본으로 — 2026-08-26

**왜:** 문서가 늘면 아무도 안 고치고, 안 고친 문서는 거짓말을 한다.
실제로 25본 중 다수가 삭제된 화면·표를 가리키고 있었다.

**버린 것:** FE/BE 로 쪼개져 겹치던 것, `.cursor/rules` 로 옮겨간 규칙,
지난달 스냅샷(완성도 판정·후속 STEP), 코드가 정본인 것(파일 트리·스모크 매트릭스).

**남긴 원칙:** 표에 화면·파일 이름을 적을 거면 **실물에서 뽑는다.**
`3_화면_지도.md` 와 `5_PIPELINE_색인.md` 는 스크립트로 생성한다.

## 이모지를 쓰지 않는다

터미널·diff·검색에서 깨지고, 뜻이 사람마다 다르다.
소스 주석·규칙·커밋·UI 문구·문서 전부 해당한다.

---

## 화면 API 는 화면 자기 경로에 둔다 — 2026-08-26

**왜:** 한 컨트롤러가 base 가 다른 두 갈래를 담고 있으면, 형제 화면을 보고
`@GetMapping("/list")` 를 적었을 때 엉뚱한 URL 이 된다.

- `UserController` → 화면(`/sys/code/user-management`)과 서명(`/sys/users`)으로 **갈랐다**
- 개선조치관리 API 를 `com.haccp.tsk` 에서 `com.haccp.flow.ca` 로 **옮겼다**.
  URL 이 `/flow/ca/...` 인데 패키지가 `tsk` 여서 「URL = 폴더 = 패키지」가 깨져 있었다

**남은 예외:** 여러 화면이 함께 쓰는 축은 화면 경로가 아니다 —
문서 허브(`docs/documents`) · 양식 허브(`docs/templates`) · 서명(`sys/users`).
그건 결함이 아니라 설계다. README 에 왜인지 적었다.

---

## 없는 경로는 404 다 — 2026-08-26

`NoResourceFoundException` 이 `@ExceptionHandler(Exception.class)` 로 떨어져
**500 UNKNOWN + 스택트레이스**가 나가고 있었다.

잘못된 주소는 서버 결함이 아니다. 404 로 내리고 스택트레이스를 남기지 않는다.

**이 결함이 다른 결함을 가렸다.** HWP 양식 삭제가 죽은 URL 을 부르고 있었는데
500 이라 「서버 오류」로 보였다. 404 였으면 훨씬 빨리 드러났다.

---

## 시험은 부정만 보지 않는다 — 2026-08-26

「시스템 양식은 지워지지 않는다」만 보는 시험은 **삭제 기능이 통째로 죽어도 통과한다.**
실제로 그랬다 — 삭제 API 가 없어 500 이 났는데 「안 지워졌다」가 참이 됐다.

원인이 하나 더 있었다. 삭제 확인창의 긍정 버튼 글자가 **「확인」이 아니라 「삭제」**라
`btn(page, "확인")` 이 아무것도 못 찾고 조용히 지나갔다.

**규칙:** 막는 것을 볼 때는 **되는 것도 같이 본다.**
그리고 확인창을 실제로 눌렀는지 응답 코드로 확인한다.

---

## 생성 문서에는 생성기를 둔다 — 2026-08-26

`3_화면_지도.md` 와 `5_PIPELINE_색인.md` 는 「손으로 고치지 않는다」고 적혀 있었지만
**뽑는 스크립트가 없었다.** 그래서 색인은 태그 하나에 파일 하나만 싣고 있었고
(태그는 1:N 인데 표는 1:1), 새로 넣은 `mesSec.ts` 가 색인에서 빠져 있었다.

```sh
node scripts/gen_screen_map.mjs         # 화면 지도
node scripts/gen_pipeline_index.mjs     # PIPELINE 색인
    --check                             # 어긋나면 실패 (CI)
```

Node 만 있으면 된다 — FE 빌드에 이미 필요하고, DB 접속이 없어도 돈다
(메뉴 이름은 `02_seed.sql`, 화면 컴포넌트는 `screenRegistry.tsx` 에서 읽는다).
