## 화면을 28개로 줄였다 — 2026-08-25

**전:** 화면 100개 이상. 대부분 껍데기이거나 한 번도 안 쓰인 것.

**왜:** 쓰지 않는 화면이 메뉴·권한·문서·시험을 전부 무겁게 했다.
「이 화면 살아 있나」를 매번 확인해야 했다.

**한 것:** 실제로 쓰는 28화면만 남기고 나머지 화면·표·SP·메뉴를 지웠다.
`tbl_screen` 103 → 28, 표 71 → 53, 양식 73 → 48.

**대가:** 나중에 그 기능이 필요하면 다시 만들어야 한다.
git 이력에는 남아 있다.

## 업무 SQL 을 전부 SP 에 둔다

**왜:** 화면이 늘어도 서버 코드는 「SP 를 부르고 결과를 담아 넘기는」 모양이 안 바뀐다.
SQL 이 자바와 XML 에 흩어지면 같은 조건이 여러 곳에 복제된다.

**규칙:** 매퍼 XML 에 직접 `SELECT` 를 적지 않는다.

**실제로 어겼을 때:** 삭제차단 SQL 이 매퍼 5곳에 복제돼 있었다.
상태 코드가 하나 늘면 여섯 곳을 고쳐야 했다 — 2026-08-26 에 공용 SP 로 내렸다.

---

## SP 를 `CREATE OR REPLACE` 로 쓴다 — 2026-08-26

**왜:** `CREATE PROCEDURE` 로 쓰면 두 번째 적용부터 실패한다.
`apply-all.sh` 는 「몇 번을 돌려도 결과가 같다」고 주장하는데 실제로는 아니었다.
운영에서 SP 하나 고치려면 손으로 DROP 해야 했다(E2E-002).

## 양식코드를 SP 안에 나열하지 않는다 — 2026-08-26

**왜:** 정규식 화이트리스트(`^hwp_sys_0(0[1-9]|1[0-9]|2[0-7])$`)가 SP 두 곳에 있었다.
`hwp_sys_028` 부터는 등록해도 목록에 안 떴다 — **열한 종이 조용히 숨어 있었다.**

**대신:** `tbl_template.doc_kind` 처럼 값으로 판단한다.

**뒷이야기 (2026-08-31):** 숨어 있던 그 열한 종은 결국 **지웠다.**
목록에 나오게 만들어 놓고 보니 **볼륨에 실물 `.hwp` 가 없어** 골라도 안 열렸다 —
등록만 되고 파일은 한 번도 올라간 적이 없는 껍데기였다(문서 0건).
지금 시스템 제공 HWP 는 `hwp_sys_001`~`027` 27종이다.
**교훈은 그대로다** — 목록에서 숨기는 것과 지우는 것은 다른 결정이고,
숨겨 두면 그게 살아 있는 줄 알게 된다.

## 목록 배지를 3단계로 보여 준다 — **폐기, 상태 코드 4개가 정본**

옛 결정: DB 다섯(`WRK`·`REQ`·`REV`·`APV`·`RJT`)을 배지 셋으로 묶는다.

반려(`RJT`)는 전송대기로 다시 고칠 수 있다.

## 공통코드 `main_cd`·`sub_cd` 를 UPPER_SNAKE 로 — 2026-08-25

**왜:** 표기가 섞여 있어 콤보가 비는 일이 잦았다.

**핵심:** `sub_cd` 는 **업무 표에 저장되는 값과 같은 표기**다.
`tbl_template.doc_kind = 'HTML'` 이면 `sub_cd` 도 `HTML` 이다.
코드만 바꾸고 데이터를 안 바꾸면 라벨이 안 붙는다 — 항상 같이 옮긴다.

**지켜지지 않은 칸 하나:** `tbl_schedule_rule.nonwork_rule` 은 저장이 소문자다 —
저장 SP(`01_sp.sql` 의 `sp_schedule_cycle_management_c_000`)가 `lower()` 로 접는데
공통코드 `sub_cd` 는 `KEEP|PREV|NEXT` 대문자다. FE·Java 가 비교 전에 대문자로 올려서 붙는다.
어느 쪽도 혼자 고치지 않는다 (`.cursor/rules/07-haccp-db.mdc`).

**대가:** 저장된 데이터까지 마이그레이션해야 했다(`04_migrate_code_upper.sql`).

## 화면 API 는 화면 자기 경로에 둔다 — 2026-08-26

**왜:** 한 컨트롤러가 base 가 다른 두 갈래를 담고 있으면, 형제 화면을 보고
`@GetMapping("/list")` 를 적었을 때 엉뚱한 URL 이 된다.

- `UserController` → 화면(`/sys/code/user-management`)과 서명(`/sys/users`)으로 **갈랐다**
- 개선조치관리 API 를 `com.haccp.tsk` 에서 `com.haccp.flow.ca` 로 **옮겼다**.
  URL 이 `/flow/ca/...` 인데 패키지가 `tsk` 여서 「URL = 폴더 = 패키지」가 깨져 있었다

**남은 예외:** 여러 화면이 함께 쓰는 축은 화면 경로가 아니다 —
문서 허브(`docs/documents`) · 양식 허브(`docs/templates`) · 서명(`sys/users`).
그건 결함이 아니라 설계다. README 에 왜인지 적었다.

## 없는 경로는 404 다 — 2026-08-26

`NoResourceFoundException` 이 `@ExceptionHandler(Exception.class)` 로 떨어져
**500 UNKNOWN + 스택트레이스**가 나가고 있었다.

잘못된 주소는 서버 결함이 아니다. 404 로 내리고 스택트레이스를 남기지 않는다.

**이 결함이 다른 결함을 가렸다.** HWP 양식 삭제가 죽은 URL 을 부르고 있었는데
500 이라 「서버 오류」로 보였다. 404 였으면 훨씬 빨리 드러났다.

## 시험은 부정만 보지 않는다 — 2026-08-26

「시스템 양식은 지워지지 않는다」만 보는 시험은 **삭제 기능이 통째로 죽어도 통과한다.**
실제로 그랬다 — 삭제 API 가 없어 500 이 났는데 「안 지워졌다」가 참이 됐다.

원인이 하나 더 있었다. 삭제 확인창의 긍정 버튼 글자가 **「확인」이 아니라 「삭제」**라
`btn(page, "확인")` 이 아무것도 못 찾고 조용히 지나갔다.

**규칙:** 막는 것을 볼 때는 **되는 것도 같이 본다.**
그리고 확인창을 실제로 눌렀는지 응답 코드로 확인한다.

## 문서 검수는 md 만 고친다 — 2026-09-03

**전:** 같은 날 두 세션이 갈렸다. 한쪽은 「검수는 md 만, 코드는 보고만」을 메모리에
고정했고, 다른쪽은 검수 순서를 승인·진행하다가 코드까지 고쳤다. 작업 트리에
검수 문서와 기능 변경이 섞였다.

**왜 md 만인가:** 검수는 「문서가 실물을 맞추는가」를 가리는 일이다. 코드를 같이
고치면 (1) 검수가 자기가 바꾼 코드를 다시 근거로 삼고 (2) 커밋이 갈라지지 않으며
(3) 생성기(`docs/5`·`docs/9`)가 아직 안 올라간 소스에 맞춰져 CI 가 깨진다.

**규칙:**

| 단계 | 고치나 |
|---|---|
| `/doc-audit` · Critic · Defender · Supervisor | **문서만.** 코드는 읽고 지적만 |
| 코드 패치 | 검수 보고를 본 사용자가 **따로** 지시할 때. 다른 커밋 |

서브는 `Read`·`Grep`·`Glob` 만 쓴다. 생성기를 돌리거나 소스를 쓰는 손은 이 루프에 없다.
절차 정본: `.claude/commands/doc-audit.md`.

## HTML 양식코드는 `html_` — 2026-09-03

**전:** CCP HTML 4계열(검증점검·포장·가열·금속검출)이 `tml_ccp_*` 로 채번돼 있었다.
표·SP 도 `tbl_tml_ccp_*` · `sp_tbl_tml_ccp_*`.

**왜:** 공정점검은 이미 `html_hyg_prc_*` 다. 같은 HTML 양식인데 접두만 다르면
채번·검색·문서가 갈린다. `tml_` 은 템플릿 약자였는데 HTML 종류를 안 말한다.

**한 것:** 행은 지우지 않는다. `tml_ccp_*` → `html_ccp_*` 로 UPDATE/RENAME.
운영·시험에 적용한 뒤 1회용 스크립트는 지웠다. 빈 DB 는 00+01+02 가 처음부터 `html_`.

**안 바꿈:** `html_sys_*` · `html_hyg_prc_*` · `hwp_sys_*` · `scrnCd` · `persistId` · 이미 발급된 `doc_no`.

**대가:** 옛 접두로 남은 백업을 복구하면 정본과 안 맞는다. 다시 옮기려면 git 이력의 `08_rename_tml_html.sql` 을 본다.

## HTML 사용양식은 지면 버전이 있어야 한다 — 2026-09-03

**전:** `02_seed.sql` 이 회사 카탈로그(`tbl_template` · `tbl_company_template` · `tbl_doc_no_rule`)만
넣고 지면 버전(`tbl_html_*_ver`)은 빼 두었다. 문서주기는 카탈로그를 읽고, 양식관리는 버전을 읽는다.

**왜:** 주기 목록에만 뜨고 양식관리에는 없어 화면에서 지울 수도 없다.

**한 것:** 문서 없는 고아 카탈로그를 시험 DB 에서 지운다. 시드 INSERT 도 뺀다.
주기 목록 SP 는 HTML 에 사용 중인 버전이 있을 때만 보여 준다. HWP 는 그대로.
복사 원본 `*_000` · `html_sys_001` · `html_sys_006` 은 남긴다.

**회사 지면은 `07_company_forms.sql` 이 표준에서 복사한다.** 시드에 회사 HTML 코드를 미리 넣지 않는다.

## 결재는 기안·결재 2단이다 — 2026-09-03

**전:** 결재선이 작성·검토·승인 3단이었다. 검토는 기본 `use_yn=N` 으로 꺼 두었는데,
코드·공통코드·SP·화면에 `REVIEW`/`REV` 가 남아 있었다.

**왜:** 현장은 검토를 쓰지 않는다. 꺼 둔 단계가 스냅샷에 섞이면 결재가 멈춘다.
결재첨부 화면은 HWP 본문(`HWP_SRC`)을 첨부 목록에 그려 「0개」 밑에 본문 파일이 보였다.

**한 것:** 검토 단계와 `DOC_STATUS.REV`·`APPR_ROLE.REVIEW`·`APPR_ACTION.REVIEW` 를 시드·SP·화면에서 지웠다.
기본 결재선은 `WRITE` → `APPROVE`. 「승인」은 항상 `APPROVE`.
결재첨부는 원본 파일(다운로드만)과 첨부 파일(추가·삭제)을 나눈다.
운영·시험 DB 에 적용한 뒤 `08_remove_review.sql` 은 지웠다. 정본은 `00_ddl`·`01_sp`·시드다.

**대가:** 검토를 다시 넣으려면 결재선·전이 SP·화면을 새로 짠다.

## 결재 4화면 이름·잔재를 맞춘다 — 2026-09-03

**전:** 화면코드는 `sign-ready`/`sign-ok` 인데 API 는 `/approval-inbox`/`/approval-history`,
SP 는 `sp_tbl_document_appr_inbox_r_000`/`_hist_r_000` 이었다.
`tbl_document.reviewer_id`·`review_dt` 와 status DEFAULT `TMP` 가 남아 있었다.
전송 버튼은 결재첨부가 툴바와 따로 구현돼 확인 문구가 갈렸다.

**왜:** 같은 흐름을 세 가지 이름으로 부르면 고칠 때 빠뜨린다. 검토 컬럼은 읽히지 않는데 상세 SP 가 계속 SELECT 했다.

**한 것:**
- API `GET /sign-ready` · `GET /sign-ok`, SP `sp_sign_ready_r_000` · `sp_sign_ok_r_000`
- reviewer 컬럼 삭제, status DEFAULT `WRK`
- 꺼 둔 `REVIEW` 결재선 단계를 지우고 승인 순번을 2 로 당김
- 전송/전송취소를 `DocumentApprovalToolbar` 로 일원화. 섹션 제목·사유·첨부 카드·스테퍼 색을 공용 컴포넌트로 모음
- 운영·시험 DB 에 적용한 뒤 `09_rename_appr.sql` 은 지웠다. 정본은 `00_ddl`·`01_sp` 다.

**안 바꾼 것:** `scrnCd`·그리드 `persistId`(`doc-approval-inbox` 등). 열 너비가 날아간다.

## JSON SP 는 넓은 화면 1개 CUD 만 — 2026-09-07

**전:** HACCP 시정조치가 jsonb payload 를 쓴 뒤, 같은 모양이 복제되기 쉬웠다.
규약이 없었다.

**왜:** 칸이 많은 화면은 인자 목록이 길어진다. 그렇다고 전 SP 를 `(p_co_cd, p_user_id, p_json)` 로
통일하면 계약이 문자열이 된다. 오타·타입은 런타임 SP 파싱에서만 터진다.

**한 것:** 허용 기준을 여기 못 박는다.

- **허용:** 화면 1개 전용 CUD 이고 컬럼이 많아 인자 목록이 깨질 때 jsonb 1개
- **금지:** 기준정보(코드·사용자·부서·메뉴·권한) typed 인자를 jsonb 로 바꾸기
- **금지:** 전 화면 통일. 새 화면은 기본 typed

이미 jsonb 인 것(`sp_tbl_hyg_process_c_000` · `sp_ccp_verify_c_000` · 시정조치)은 유지한다.

## HTML 출력만 살균한다 — 2026-09-07

**전:** 전역 `<>` strip·Lucy 필터를 넣을지 논의했다.

**왜:** `<10℃` 와 양식 원문을 파괴한다. XSS 는 출력 문제다.

**한 것:** 전역 strip 금지. 프로덕션 `dangerouslySetInnerHTML` 0건을 유지한다.
HTML 을 **렌더하는 한 지점**이 생기면 그 싱크에만 DOMPurify 를 붙인다.
미리보기·내보내기가 생기기 전에는 의존성을 넣지 않는다.

## 변경 감사는 fail-closed, 조회로그는 fail-open — 2026-09-07

**왜:** 규제 문서의 변경 이력이 비면 저장만 되고 감사가 빈다.
조회/통계 로그 락이 본업을 막으면 현장이 멈춘다.

**한 것:**
- 변경 감사(`AuditWriter`)는 같은 TX. 저장이 롤백되면 이력도 같이 사라진다
- 조회로그(`useViewLog`)는 실패를 삼킨다

감사도 삼키라는 처방은 기각한다.
