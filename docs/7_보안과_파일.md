## 1. 시크릿

| 해도 됨 | 하면 안 됨 |
|---|---|
| `*.env.example` · `.env.docker.example` | `.env` · `.env.docker` · `*_secret*` |
| Jenkins Credentials (`haccp-*`) | Jenkinsfile·compose 에 실값 |
| 서버 `.env.docker` (권한 0600) | git commit · PR 첨부 |

커밋 전 검사:

```sh
bash scripts/pre-commit-check-secrets.sh
# 훅으로 걸기
ln -sf ../../scripts/pre-commit-check-secrets.sh .git/hooks/pre-commit
```

기동에 필요한 값: `JWT_SECRET` · `DB_HOST` · `DB_USERNAME` · `DB_PASSWORD`.

## 2. 인증 — JWT

```
로그인  POST /api/v1/auth/login   ← 인증이 없는 유일한 경로
        ↓ BCrypt 비교 · 잠금 판정
        JwtProvider.createToken   HS512
        sub · coCd · coNm · userNm · usrgrpCd · deptCd · sid
        ↓
모든 요청  Authorization: Bearer …
        JwtFilter → LoginUserContext 에 담는다
```

| 규칙 | 왜 |
|---|---|
| **본문의 `coCd`·`userId` 를 믿지 않는다** | 서비스가 `LoginUserContext` 값으로 덮어쓴다. 안 그러면 남의 회사 자료를 쓴다 |
| 비밀번호는 BCrypt 해시로만 저장 | `tbl_user.user_pw` 가 `$2a$` 로 시작하고 60자여야 한다 |
| 로그인 **실패도** 기록한다 | 성공만 남기면 침입 시도를 못 본다 |
| 실패 누적이 임계에 닿으면 잠근다 | `app.login.max-fail-count` |

E2E 가 위조 본문(`coCd:"9999"`)을 보내 덮어쓰기를 확인한다.

## 3. 권한 — 두 겹

| 겹 | 어디 | 막는 것 |
|---|---|---|
| 1 | `JwtFilter` | 토큰 없음·서명 틀림·만료 → 401 |
| 2 | `ScreenAuthInterceptor` + `ScreenAuthResolver` | 그 화면·그 동작 권한 없음 → 403 |

**맵에 없는 경로는 2겹째를 그냥 지나간다 — 등록 누락은 열린 문이다.**
`ScreenAuthResolver.resolve` 가 `Optional.empty()` 를 주면 인터셉터가 로그도 없이 통과시킨다.
새 API 를 만들면 반드시 맵에 등록한다 (`docs/2_화면_추가하기.md` 4단계).

권한은 `tbl_role_screen` (회사 × 그룹 × 화면 × 읽기/쓰기/수정/삭제/출력)에 있다.
`usrgrpCd == 'ADMIN'` 은 전권이며 화면권한 목록을 조회하지 않는다.

**화면이 버튼을 숨겼다고 막힌 게 아니다.** API 를 직접 쳐도 막혀야 한다 —
E2E `security-constraints` 가 이걸 확인한다.

| 그룹 | 읽기 | 쓰기 | 수정 | 삭제 |
|---|---|---|---|---|
| ADMIN | 29 | 29 | 29 | 29 |
| USER | 17 | 16 | 16 | 1 |
| VIEWER | 18 | 0 | 0 | 0 |

정본은 `db_sasshaccp/02_seed.sql` 의 `tbl_role_screen` 0000 블록이다 (29화면 기준).

- **USER 는 12화면에 권한행이 아예 없다** — 결재완료 · 사용양식관리 · 문서주기관리 · 시스템 9화면.
  없는 것은 「N」이 아니라 행이 없는 것이다
- USER 삭제는 **결재첨부(`attach`) 하나만** `Y` 다
- `calendar`(일정) 는 USER 에게 읽기·출력만이다
- VIEWER 가 못 읽는 11화면은 **시스템 관리·이력 9화면 + 사용양식관리 + 문서주기관리**다

## 4. 오류를 어떻게 내보내나

| 원인 | 상태 | 코드 | 사용자가 보는 것 |
|---|---|---|---|
| 업무 규칙 위반 (SP `45000`) | 400 | `DB_SIGNAL` | SP 가 쓴 문구 그대로 |
| 입력이 틀려 DB 가 거절 (`22001`·`23502`·`23503`·`22P02`) | 400 | `BAD_INPUT` | 「입력한 값이 너무 깁니다」 등 |
| 동시 처리 충돌 (`23505`·`40P01`) | 409 | `CONFLICT` | 「잠시 후 다시 시도」 |
| 그 밖 | 500 | `DB_ERROR` | 「데이터 처리 중 오류」 + 서버 로그 |

**입력이 틀린 것을 500 으로 내지 않는다.** 사용자가 무엇을 고쳐야 할지 모르고,
로그에서 진짜 장애와 구분이 안 된다.

## 5. 업로드 파일

| 항목 | 값 | 설정 |
|---|---|---|
| 저장 위치 | `${APP_FILE_ROOT:./data/haccp-files}` | 서버 디스크. **DB 에 바이너리를 넣지 않는다** |
| 한 파일 최대 | 20MB | `APP_FILE_MAX_SIZE` · `APP_FILE_MAX_BYTES` |
| 요청 최대 | 25MB | `APP_FILE_MAX_REQUEST_SIZE` |
| 경로 규칙 | `{root}/HaccpLogBooks/{co_cd}/{tmpl_cd}/{yyyy-MM-dd}/{yyyy-MM-dd}_{원본명}_{연번}.{확장자}` | 회사·양식·일자로 나눈다. 양식과 무관한 첨부는 `{tmpl_cd}` 단을 생략한다. 하위 루트명은 `app.document.logbook-directory`(`APP_DOCUMENT_LOGBOOK_DIRECTORY`, 기본 `HaccpLogBooks`) |
| DB 에 남는 것 | 경로·파일명·크기 | `tbl_document_file` · `tbl_company_template_file` |

**경로 탈출을 막는다.** `DocumentFileStorage.resolve` 가 상대 경로를 root 안으로만
해석하고, root 밖이면 `BizException` 이다.

파일을 지울 때 DB 행만 지우고 디스크를 남기면 용량이 샌다 — 반대도 마찬가지다.
`tools/reset_test_documents.sql` 은 DB 만 비운다(주석에 명시).

## 6. 삭제

**HTTP DELETE 를 쓰지 않는다.** 두 단계다.

```
POST /validate-delete   지울 수 있는지 먼저 본다 (참조 검사)
      ↓ 확인창
POST /delete            서버에서 같은 검사를 한 번 더 한다
```

두 번 검사하는 이유 — 확인창이 뜬 사이에 상태가 바뀔 수 있고,
화면을 거치지 않고 API 를 직접 칠 수도 있다.

지우는 방식은 표마다 다르다.

| 표 | 방식 |
|---|---|
| `tbl_document` | `del_yn = 'Y'` (소프트) |
| 기준정보 (부서·사용자·코드) | `use_yn = 'N'` 또는 실제 삭제 |
| 문서 상태 | `status` 로 관리. 전송·결재완료는 못 지운다 |

## 7. 감사

| 무엇 | 어디 | 남기는 시점 |
|---|---|---|
| 기준정보 변경 | `tbl_audit_log` | 저장·삭제마다 (6화면 전부) |
| 로그인 | `tbl_login_log` | 성공·실패·잠금 모두 |
| 화면 조회 | `tbl_view_log` → `tbl_view_stat_daily` | 화면 이동 시 모아 보낸다 |
| 결재 | `tbl_document_approval` | 단계마다. 서명 스냅샷 포함 |

**감사 로그는 지우지 않는다.** `tbl_audit_log` 주석에 명시돼 있다.

결재선 변경은 한동안 감사에 안 남았다(E2E-003). 「누가 결재하는가」를 정하는 화면이라
흔적이 없으면 안 된다 — 지금은 남긴다.

## 8. 서명

서명은 **바이너리**(`bytea`)다. 파일 경로가 아니다.

| 표 | 칸 |
|---|---|
| `tbl_user` | `sign_img` · `sign_mime` · `sign_nm` |
| `tbl_document_approval` | `sign_img` (결재 시점 스냅샷) |
| 지면 표 | `sign_img` (행 서명 스냅샷) |

**옛 `sign_path` 를 참조하면 결재가 통째로 죽는다.**
실제로 SP 하나가 안 따라와 전송·승인·반려가 전부 500 이었다(E2E-001).

스냅샷을 뜨는 이유 — 사용자가 나중에 서명을 바꿔도 **그때 결재한 서명**이 남아야 한다.

### 올린 MIME 은 믿지 않는다

서명은 **밖에서 들어온 바이트가 우리 도메인으로 되돌아 나가는** 유일한 경로다
(`inline` 으로 그림을 띄운다).

2026-08-27 이전에는 올린 쪽이 보낸 `Content-Type` 을 그대로 `sign_mime` 에 저장했고,
조회가 그 값을 그대로 응답 `Content-Type` 에 실었다.
검사도 「확장자 **또는** 타입」이라 한쪽만 맞으면 통과했다 —
`sign.png` 를 `Content-Type: text/html` 로 올리면 우리 도메인에서 열리는 HTML 이 됐다.

| 지금 | |
|---|---|
| 저장 MIME | **확장자에서만** 정한다 (`UserService.guessImageMime`). 올린 쪽 값은 안 쓴다 |
| 검사 | 확장자 **그리고** 타입이 둘 다 `png`·`jpg`·`jpeg` 라야 통과 |
| 겹으로 | `SecurityHeadersFilter` 가 전 응답에 `X-Content-Type-Options: nosniff` |
| 크기 | 10MB 이하 (`SIGN_MAX_BYTES`) |

시험은 `UserServiceSignTest` — **저장되는 MIME 값**을 본다.
통과·거절만 보면 이 결함을 다시 못 잡는다.
